> Цю статтю навмисно знеособлено: без секретів, реальних доменів, назв кластерів і внутрішніх ідентифікаторів.

## Проблема

У test/sandbox-середовищі сканер вразливостей працював нестабільно:
- періодично зникали результати сканування;
- частина задач завершувалась із таймаутом;
- звіти з’являлися нерівномірно після деплою.

Мета: отримати передбачуваний і повторюваний цикл сканування без зайвого навантаження на кластер.

## Діагностика

Що перевірив у першу чергу:

```bash
kubectl get pods -n security
kubectl get events -n security --sort-by=.lastTimestamp
kubectl logs deploy/trivy-operator -n security --tail=200
kubectl top nodes
```

Спостереження:
- сплески помилок збігались із піками навантаження;
- частина job-сканів стартувала одночасно і конкурувала за ресурси;
- дефолтні налаштування були занадто агресивні для sandbox.

## Рішення

У values-конфігурації застосував консервативний профіль для sandbox:
- обмежив паралельність сканування;
- задав явні requests/limits;
- увімкнув більш передбачуваний ритм сканів;
- скоротив набір сканованих сутностей до пріоритетних.

```yaml
operator:
  scanJobsConcurrentLimit: 2

resources:
  requests:
    cpu: 100m
    memory: 256Mi
  limits:
    cpu: 500m
    memory: 512Mi

scan:
  skipNonCriticalNamespaces: true
  retryBackoff: "30s"
```

## Перевірка результату

Після змін перевірив:
- стабільність подів оператора протягом кількох циклів;
- відсутність хвилі таймаутів у scan jobs;
- рівномірну появу звітів після релізів.

## Що далі

Наступні ітерації для production-підходу:
- розвести профілі налаштувань за середовищами;
- додати алерти на деградацію сканування;
- зафіксувати SLO за часом публікації результатів.
